# Grandmaster Hardware Improvements: High-Precision Timestamping (Dual PIO Method)

This document outlines the correct, high-precision method for timestamping the GPS PPS signal in hardware on the RP2040. This is an advanced technique that yields a timestamp free from software-induced latency and jitter, which is the ideal input for a high-accuracy GPS-Disciplined Oscillator (GPSDO).

This implementation uses two state machines on the same PIO instance:
1.  **SM0 (Timer):** Runs a free-running 32-bit counter, acting as a high-resolution, local PIO clock.
2.  **SM1 (Capture):** Watches the GPS PPS input pin. When it detects a rising edge, it instantaneously captures the current value of SM0's counter and pushes it to its FIFO for the CPU to read.

### 1. The PIO Program (`pps_dual.pio`)

Create a new file `pps_dual.pio` in your `pio/` directory. This single file will contain two separate programs. Note that we do not use the C-SDK block here, as the initialization is custom.

**File: `pio/pps_dual.pio`**
```pioasm
; PIO Program for dual-SM PPS timestamping

; --- Program 1: PIO Timer ---
; A 32-bit free-running decrementing counter using the X scratch register.
.program pio_timer
    set x, 0xFFFFFFFF   ; Initialize counter to max value on reset
.wrap_target
    jmp x--             ; Decrement X each clock cycle
.wrap


; --- Program 2: PIO Capture ---
; Waits for a rising edge, then captures the other SM's X register value.
.program pio_capture
.wrap_target
    wait 0 pin 0        ; Wait for pin to go low
    wait 1 pin 0        ; Wait for rising edge of PPS signal
    in x, 32            ; Immediately sample the other SM's X register into ISR
    push                ; Push the 32-bit timestamp to the RX FIFO
.wrap
```

You will need to use `pioasm` to convert this file into a C header (`pps_dual.pio.h`) as part of your build process.

### 2. C Implementation (`grandmaster/gps.c`)

This section details the necessary changes in your C code to initialize and run the two PIO state machines and handle the resulting timestamps.

#### Step 2a: State Machine and IRQ Configuration

The `gps_init` function will be repurposed to set up this new system. The old PIO initialization for PPS capture should be removed. We will use a PIO interrupt to signal that a new timestamp has been pushed to the FIFO.

```c
#include "hardware/pio.h"
#include "hardware/irq.h"
#include "pico/stdlib.h"
#include "pps_dual.pio.h" // The header generated by pioasm

// Choose a PIO instance
#define PPS_PIO pio0

// State machine definitions
static uint sm_timer;
static uint sm_capture;

// Captured PPS timestamp from PIO
static volatile uint32_t last_pps_pio_timestamp;
static volatile bool pps_available;

// Forward declaration for the new IRQ handler
static void pps_irq_handler();

void gps_init_pps_capture(uint pps_pin) {
    // --- Claim and configure state machines ---
    sm_timer = pio_claim_unused_sm(PPS_PIO, true);
    sm_capture = pio_claim_unused_sm(PPS_PIO, true);

    // --- Load programs into PIO memory ---
    uint offset_timer = pio_add_program(PPS_PIO, &pio_timer_program);
    uint offset_capture = pio_add_program(PPS_PIO, &pio_capture_program);

    // --- Configure Timer SM (SM0) ---
    pio_sm_config c_timer = pio_timer_program_get_default_config(offset_timer);
    // Run as fast as possible (sys_clk / 1). Each `mov` takes 1 cycle.
    sm_config_set_clkdiv(&c_timer, 1.0f);
    pio_sm_init(PPS_PIO, sm_timer, offset_timer, &c_timer);

    // --- Configure Capture SM (SM1) ---
    pio_sm_config c_capture = pio_capture_program_get_default_config(offset_capture);
    // Set the input pin for `wait`
    sm_config_set_in_pins(&c_capture, pps_pin);
    pio_sm_set_consecutive_pindirs(PPS_PIO, sm_capture, pps_pin, 1, false);
    pio_gpio_init(PPS_PIO, pps_pin);
    // Shift 32 bits from ISR to RX FIFO automatically on `push`
    sm_config_set_in_shift(&c_capture, false, true, 32);

    pio_sm_init(PPS_PIO, sm_capture, offset_capture, &c_capture);

    // --- Configure Interrupts ---
    // Clear any pending interrupts
    pio_interrupt_clear(PPS_PIO, 0);
    pio_interrupt_clear(PPS_PIO, 1);

    // Enable interrupt on RX FIFO not empty for the capture SM
    pio_set_irq0_source_enabled(PPS_PIO, pis_sm1_rx_fifo_not_empty, true);
    irq_set_exclusive_handler(PIO0_IRQ_0, pps_irq_handler);
    irq_set_enabled(PIO0_IRQ_0, true);

    // --- Enable both state machines simultaneously ---
    // This ensures their relative timing is consistent.
    pio_enable_sm_mask_in_sync(PPS_PIO, (1u << sm_timer) | (1u << sm_capture));

    printf("Dual PIO PPS capture ready on pin %d\n", pps_pin);
}
```

#### Step 2b: The New Interrupt Handler

The PIO interrupt handler is now much simpler. It is triggered when the capture SM pushes a timestamp. Its only job is to read that value from the FIFO.

```c
static void __time_critical_func(pps_irq_handler)() {
    // Check if the interrupt is from our capture SM's RX FIFO
    if (pio_get_irq0_source(PPS_PIO) == pis_sm1_rx_fifo_not_empty) {
        // Read the timestamp. No need to clear IRQ source, reading FIFO does that.
        last_pps_pio_timestamp = pio_sm_get(PPS_PIO, sm_capture);
        pps_available = true;
    }
}
```

#### Step 2c: Retrieving the Timestamp

Your discipline loop on Core 1 will call a function to get this new PIO timestamp. This function replaces `gps_get_pps`.

```c
// In gps.h
typedef struct {
    uint32_t pio_timestamp;
    bool valid;
} gps_pps_t;

bool gps_get_pps(gps_pps_t *pps);

// In gps.c
bool gps_get_pps(gps_pps_t *pps) {
    if (!pps_available) {
        return false;
    }
    pps->pio_timestamp = last_pps_pio_timestamp;
    pps->valid = gps_has_fix(); // Assumes gps_has_fix() still exists
    pps_available = false;
    return true;
}
```

### 3. Adapting the Discipline Algorithm

The key insight is that the PIO timestamp is **relative**, not absolute. It's a 32-bit counter that wraps. The absolute value doesn't matter; what matters is the **difference** between timestamps.

Your discipline algorithm in `common/discipline.c` needs to be adapted to work with this high-resolution relative time.

**Conceptual changes for `discipline_update_reference`:**

1.  **Calculate Expected Ticks:** You know the PIO timer SM's frequency (e.g., `sys_clk / 1 = 125 MHz`). You can calculate the exact number of PIO ticks expected in one second (`expected_pio_ticks = 125,000,000`).

2.  **Calculate Actual Ticks:** When you get a new PPS timestamp, calculate the difference from the last one, accounting for the 32-bit wrap-around.
    ```c
    uint32_t last_ts = clock->last_reference_pio_ts;
    uint32_t new_ts = new_pps_event.pio_timestamp;
    // For a decrementing counter, elapsed ticks = last_ts - new_ts.
    // Standard 32-bit integer wrapping handles the rollover correctly.
    uint32_t actual_pio_ticks = last_ts - new_ts;
    ```

3.  **Calculate Phase Error in Ticks:** The phase error is now simply the difference between the actual and expected tick counts.
    ```c
    int64_t phase_error_ticks = (int64_t)actual_pio_ticks - (int64_t)expected_pio_ticks;
    ```

4.  **Feed into PI Controller:** This `phase_error_ticks` value is the high-precision signal your PI controller needs. You can convert it to nanoseconds (`phase_error_ns = phase_error_ticks * 8` if running at 125MHz) before feeding it into your existing floating-point PI logic.

This method provides an extremely clean and precise phase error measurement, allowing your GPSDO to achieve the highest possible accuracy on this hardware.
